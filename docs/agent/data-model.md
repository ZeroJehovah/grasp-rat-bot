# Current Data Model


- The page owns the game WebSocket lifecycle. The bot must not create or reconnect a second socket.
- Control should use the page/native WebSocket and native page state when available. The bot may send `vel` and `shoot` messages directly on the existing native page WebSocket for lower command-path overhead, but it must not create or reconnect a second socket.
- A current user id plus page/native WebSocket in `CONNECTING` or `OPEN` state counts as an active page game session for login/status purposes, even if `tmpGameSessionToken` is unavailable. The exception is a fresh `graspRatNoSelfSnapshotRecovery` marker written after snapshot-confirmed server-side exit; while that marker matches the current user and self is still missing, stale token/native-session evidence is ignored only until recovery login has been started. After the marker records `loginStartedAt`, automatic login waits through the recorded `bot login started` grace instead of clicking the login control again during an OAuth callback/page reload gap.
- Confirmed exits and successful/HTTP 403 leave completions must stop game-operation motion immediately. The stop path clears native movement keys, velocity vectors, `lastVel`, touch movement, and any pending precision pulse timer before the bot continues relogin/hold bookkeeping. Pending-exit confirmation also requests the normal page reload path after `exit-confirmed`, so the native page clears stale WebSocket reconnect timers and motion state.
- Tampermonkey and extension bootstraps can pass persisted runtime config to the remote bot, including combat logging enabled/address.
- Bootstrap panel follows the native left-side panel visual language: 336px right rail, 16px radius, translucent dark rail background, native monospace font, status dot, compact dot pause/resume control, and compact metric cards for session uptime/stamina spent/coins/kills.
- Bootstrap panel header uses compact dots: `BOT` dot toggles pause/resume, `WS` dot shows online/connecting/offline state, the remote-log dot toggles combat logging, and a compact dynamic-width network-quality pill follows those controls before the right-side GitHub link. The network pill displays `latency/loss` such as `123ms/0.00%`, using `??ms/??.??%` until samples exist; latency and loss are colored independently and the slash remains white. The clock row shows current time and two dashed-circle icon buttons: red sets the page-native view radius to `15100cm` (151m), and blue sets it to `50200cm` (502m). The displayed latency is an effective game latency estimate that prefers recent movement action confirmation and falls back to native WebSocket state-frame timing; displayed packet loss is estimated from native WebSocket state-frame long gaps over the rolling runtime window.
- `status().networkQuality` exposes the full rolling estimate: displayed latency/loss, latency/loss source labels, native WebSocket frame interval/jitter/gap counts, current stall state, and movement/attack action feedback counters. The state is in-memory only and is intentionally recomputed after reload or hot update.
- `status().actionSettlementStall` exposes the in-memory detector for the case where the native WebSocket still receives state frames and local movement/shot intent continues, but the game does not settle actions: self position, HP, stamina, coins/Drop, and combat target HP stay unchanged while movement acknowledgements are stale. When `actionSettlementStallOfflineEnabled = true`, a stalled state is handled by the normal offline leave path with the same safe/unsafe wait timing as websocket offline.
- `status().targetSwitchDiagnostics` exposes the in-memory final-action focus history used to diagnose target oscillation. It preserves `lastFocus`, `lastTargetFocus`, `lastSwitch`, and a capped recent `events` list across hot updates; standalone combat-log `target-switch` misc entries are emitted only when combat logging is enabled.
- `status().finalActionArbitration` exposes the final action arbitration state. It preserves `lastAction`, `lastFocus`, `lastSelectedAt`, `lastOverride`, and a capped `history` list across hot updates so short cross-band stick decisions can be inspected after live oscillation samples.
- `status().chaseMode` exposes chase-mode state for bootstrap A: `enabled`, `minDrop`, `activeCount`, `candidateCount`, `panelCandidates`, `targets`, `selectedTarget`, `lastClear`, and `lastDecision`. Candidate/target display records can include `invulnerable`, `invulnerableRemainingMs`, and `invulnerableRemainingTicks`; bootstrap A renders the remaining time in the `猎杀` panel when present. Remote B persists marked targets under `localStorage.graspRatChaseModeTargets` with normalized records (`id`, `name`, `dropAtMark`, last observed Drop/HP/position/distance/source, `markedAt`, `markedBy`) and preserves in-memory chase state across hot updates. Transient visible low-Drop observations are tracked in memory only and are not written back to target records until they mature into a real clear. Confirmed chase kills add an in-memory, hot-update-preserved `killedTargetSuppressions` entry keyed by id; this removes the target from panel/action candidates until a later explicit observation after the kill time lets the normal Drop/whitelist filters evaluate it again. Bootstrap A stores only panel visibility in `localStorage.graspRatChasePanelVisible`; that key must not affect target persistence or strategy behavior.
- Remote-log dot is green when logging is enabled, green blinking when entries are pending, yellow when disabled, and red after recent flush failures.
- Metric cards show values only; labels are exposed through `title` and `aria-label`.
- The HP line shows the three stamina windows as native remaining/limit pairs without 5s/1h/1d labels.
- Session stamina spent is derived from observed 1d stamina max/min inside the current login and tracked across UTC+8 daily resets. Runtime today totals and generated daily reports also retain the latest 1d remaining/limit pair and prefer the actual daily delta (`stamina1dLastLimit - stamina1dLastRemaining`) when it is higher than the summed per-login deltas, so mid-day logins do not undercount full-day stamina consumption.
- Important summary logs persist locally under `localStorage.graspRatImportantLogs` with `sessions`, `combats`, and replayable `events`. They record login/exit summaries, stamina/coin/kill totals, per-kill reward details, pure refreshed coin estimates, and combat HP start/end/min/max/deltas/results. Session payloads include `stamina1dObservedMax`, `stamina1dObservedMin`, `stamina1dLastRemaining`, and `stamina1dLastLimit` for report reconciliation. Per-kill summaries include `rewardConfirmed`/`dropMatched` for local picked-reward evidence, `chatConfirmed`/`killConfirmed` for confirmed kills that may not have been picked, and optional non-combat battle-window fields (`battleStartedAt`, `battleEndedAt`, `battleDurationMs`, `battleStaminaSpentMs`) for daily actual battle profit rows. The daily report treats local reward evidence conservatively and can demote over-budget rewards to unpicked Drop when session collected coins cannot cover them. Combat HP start/min/max fields use the first observed valid HP value and must not treat missing `null` as zero. When a combat-log endpoint is configured, these `important-log` events are posted to the same `/combat-log` service as non-critical logs even if normal combat logging is disabled.
- Remote bot post-login zoom state is exposed in `status().postLoginZoom`; after self is missing for at least 1s, the next alive self detection schedules a visible-range pass after a 120ms resize-stabilization delay. The pass reads the native/page view radius from native `state.viewRadiusCm`/equivalent fields first, then the `scaleText` label (`view r=...m`), and targets `postLoginZoomFitRadiusCm = 50200`. By default it calls the page-native `setViewRadius(50200)` directly (`postLoginZoomDirectSetEnabled = true`) and verifies the result against the same native/page radius stop condition. If the direct setter is unavailable or fails to reach the target after a short settle delay, it falls back to one-way centered zoom-out wheel steps while the current view radius is below 502m. Once the native view radius reaches or exceeds 502m, the pass stops and the same login/session key is not adjusted again. It never zooms back in and no longer stops after a single non-improving measurement, so a delayed label update does not abort the sequence early. Wheel fallback uses `postLoginZoomWheelDeltaY = 80`, `postLoginZoomOutIntervalMs = 80`, and is capped by `postLoginZoomFitMaxSteps = 24` / `postLoginZoomFitMaxOutSteps = 24` as a runaway guard. Fixed fallback zoom-out clicks are disabled by default (`postLoginZoomOutClicks = 0`) so unavailable view-radius measurement no longer blindly shrinks the page overnight. The no-token post-login zoom session key is stable per user, preventing no-self/self recovery jitter from re-triggering zoom repeatedly without a real new session token. The `postLoginZoom` state is preserved across remote bot hot updates, so script replacement while already in-session does not re-trigger zoom.
- When the page is already logged in/reconnecting but self entity is not visible yet, the remote status reports `game-session-connecting` with display reason `已登录，等待游戏连接/自身实体` instead of `login-cooldown`.
- A logged-in/session-present no-self state is unsafe when native WebSocket reconnect churn is detected or the own entity stays missing for `gameSessionNoSelfLeaveMs = 30000`. Visible login controls are not login-state evidence for this decision because the native/sidebar login entry can be present while the script controls it; only explicit login-required text counts as a login-required state signal. If explicit login-required text appears in the page body, chat DOM, or recent page messages while stale local/native session evidence and a missing self are present, the bot treats the local session as server-rejected immediately: it confirms `login-required-no-self-exit-confirmed`, clears the same local/session/native state, writes the recovery marker, clears pending exit state, closes the native WebSocket, and requests a reload without waiting for a fresh snapshot or calling `leave()`. If a fresh page-native `/snapshot` still contains the current self, the bot treats this as a live session/mismatch problem; if the fresh snapshot is authoritative and self is absent, it confirms the server-side exit, clears stale local/session login keys (`tmpGameSessionToken`/`tmpGameUserId` plus `tmpGameSession*`, `tmpGameUser*`, `tmpGameLogin*`, `tmpGameAuth*`, `tmpGameToken*`, and `tmpGameOAuth*` keys), preserves page preference/tutorial markers such as `tmpGameHelpSeenV3`, writes `localStorage.graspRatNoSelfSnapshotRecovery`, closes the page WebSocket, clears page-native `state.currentUserId/sessionToken/ws/wsOpen` plus cached entity arrays/reconnect timers, and requests a page reload before gated auto-login. If this no-self recovery path has already fallen through to `/leave` and the server returns HTTP 403, that 403 is treated as stale-local-session confirmation for no-self recovery only: it clears the same local/session/native state, writes the recovery marker with reason `leave-403-no-self-exit-confirmed`, clears pending-exit state, requests a page reload, and does not enter pending-exit retry or a leave-403 relogin hold. If the fallback pending exit is instead confirmed later through normal exit-confirmation evidence, and the pending exit carries `offlineSafety.noSelfGameSession`, the same local/session/native reset now runs before `requestReload('exit confirmed')`; this is required because exit-audit flushing can temporarily block reload while the old native WebSocket would otherwise keep reconnecting with stale local state. That marker suppresses repeat leave/session-mismatch handling and the generic reconnecting-session wait, ignores stale generic post-login suppress until it records that the recovery login has started, and then lets the active login grace/cooldown block duplicate OAuth/login clicks until self appears or the grace expires. Other no-self timeout/churn cases still use the offline leave path, and non-no-self leave 403 handling keeps the existing risk-control behavior.
- `status().lastHelpModalDismiss` records the most recent automatic new-player tutorial modal dismissal attempt. Runtime ticks and auto-login preparation call the page-modal helper, which only clicks a visible `#helpModal` with tutorial/help title and a visible `#helpOkBtn`/known confirmation label; this is a DOM fallback, not the primary tutorial-state mechanism.
- Native WebSocket reconnect churn is tracked from page WebSocket object/state transitions. Three offline-ish reconnect events within 10s count as `control-ws-reconnect-churn`.
- `loginSnapshotGate` is exposed in status/log context and remains the automatic relogin gate wrapper, but standalone `/snapshot` connectivity no longer has an independent 3-sample pass condition. Exit trigger and exit confirmation reset the learned login-point safety evidence; future ordinary unattended relogin is then blocked only until learned login-point safety is satisfied. Explicit manual login from the sidebar/native control is the exception: it records `manualLoginBypass` diagnostics and can bypass snapshot/login-point gates, pause state, suppress, and cooldown. `loginPointSafety` is a durable persisted gate under `localStorage.graspRatLoginPointSafety`: every successful post-login/session-recovery alive-self coordinate refresh updates the persisted login point, and exit/gate resets clear only the safety streak/evidence, never the point. The success streak is page-load scoped: the stored state includes `pageLoadAt`, and a new tab or refresh with a different `performance.timeOrigin` clears the streak, sample timestamps, stale danger/error, and movement evidence while preserving the learned point, same-day damage actors, and last-exit HP radius context. Runtime hot updates preserve `lastLoginAt`, localStorage coordinates are merged back even if in-memory state is empty or stale, newer persisted `lastExitSelfHp` context is merged back after hot updates, and reset `at/reason` plus last-exit HP context is persisted through reloads. When a point is present, future unattended relogins require `loginPointSafetySuccessRequired = 3` consecutive successful page-native `/snapshot` responses with no dangerous player inside the active radius; a `/snapshot` error or unsafe sample resets this streak to `0`. The relogin gate does not actively fetch `/snapshot`; its passive observer avoids wrapping `window.fetch` and `XMLHttpRequest.send`, then reads parsed page fetch responses through `Response.json/text` and page-owned XHR responses through a load listener installed from `open`. Snapshot errors clear stale `lastDanger` so the visible block reason is either the current player danger or the current snapshot error, not both. The radius is `loginPointSafetyHealthyRadius = 17000` only when the last recorded exit HP is at least `loginPointSafetyHealthyHpThreshold = 80`, otherwise it is the conservative `loginPointSafetyRadius = 30000`. Unknown last-exit HP is treated as low HP and uses `30000`. When no point is available, status reports `missingPoint` and the safety gate is not satisfied. Dangerous players are limited to same-day recorded damage actors and `Active` mode players with observed activity evidence; same-day damage actors are persisted only from self-HP-drop evidence that identifies the actor by incoming bullet ownership, firing evidence, or engaged-combat evidence. Pure join-mode `Active` no longer blocks by itself: the Active-mode gate requires firing, movement/speed or observed login-point movement, 5s stamina below the full threshold, or engaged-combat flags. `status().reloginGate` summarizes the visible pre-login gates for panel/log inspection without changing decisions: cooldown/suppress/hold remaining versus total and login-point safety streak out of 3 with missing-point, danger, error, active radius, and last-exit HP details. Once an alive self appears after entry, the login-point gate remains pre-login only; normal movement/combat/exit logic handles post-entry safety.
- `sessionMismatchRecovery` is exposed in status when the page/auth UI and native game session disagree. A low-risk timed-out session mismatch first writes one refresh attempt to `localStorage.graspRatSessionMismatchRecovery`; after a page load whose `performance.timeOrigin` follows that request, the same-user mismatch may proceed to the existing guarded takeover path. The marker expires after `sessionMismatchRecoveryReloadMaxAgeMs` and is cleared once self is restored or the mismatch resolves.
- Stale enemy/offline relogin holds are cleared when the page has recovered to an alive self entity and an online native WebSocket, so the panel no longer shows an old wait reason or keeps the bot stopped after recovery.
- Bootstrap manifest polling defaults to 10s. Tampermonkey request transports and raw/jsDelivr fallback URLs are tried sequentially, so a successful poll should issue only one manifest network request instead of parallel duplicate raw GitHub requests.
- Bootstrap watchdog checks a running bot's version/hash/tick health every second. When a bot is stale but still running with its timer active, the watchdog first probes `bot.step('bootstrap-watchdog-stale-probe')` and rechecks status before reinstalling cached source, so ordinary timer delay does not cause repeated same-version hot replacement.
- Ordinary in-game global refresh no longer actively fetches `/snapshot` or `/minimap`. `globalRefreshMs = 5000` only throttles passive-refresh diagnostics; runtime state is updated from native/realtime page state plus page-native `/snapshot` responses observed without wrapping request send paths.
- The old movement-time server-position forced refresh probe has been removed. Movement no longer triggers extra `/snapshot` or `/minimap` requests.
- Local/native page data is authoritative near the bot. Snapshot data is for outside-local awareness only.
- Combat target, aim, and fire decisions use native/realtime visible entities and bullets only. Realtime visual range is larger than attack range, so combat does not need snapshot data.
- Ordinary profit routing considers native/realtime visible coins and visible AFK targets. It no longer falls back to far snapshot coins or snapshot/minimap Drop targets; if no visible/native coin or acceptable visible target exists, the bot waits for visible coin refresh.
- Chase-mode target discovery may merge snapshot/minimap/persisted records for panel display and approach movement, but combat handoff still requires the marked target to be current native/realtime visible and attackable. Snapshot/minimap/persisted chase data must not be used for combat target, aim, or fire.
- `opportunityAfkStamina` is an in-memory, hot-update-preserved map keyed by target id. It stores the last observed 5s stamina sample plus a cooldown expiry; observed stamina decreases make only out-of-range AFK opportunity targets ineligible until the 60s cooldown expires.
- For coins specifically: inside the local/view authority radius, do not use `/snapshot` coin drops. Real visible/local coins must come from native page coin state.
- Native coin discovery includes the page render helper `getRenderCoinDrops()` plus native state coin/list fields; it accepts arrays, Map/Set values, object maps, single coin objects, and render/state getter functions. This is the authoritative source for visible viewport coins.
- Snapshot coins may still be classified for diagnostics/outside awareness only. Ordinary coin pickup does not navigate to snapshot-only coins, even outside `nativeCoinAuthoritativeRadius = 50000cm`.
- Native/visible coins must not receive `snapshot-coin-*` reasons even if merged metadata carries snapshot fields.
- Removed local snapshot fallback: no `snapshotCoinLocalFallbackMaxDistance`, no local snapshot/native matching fallback.
