# Current Data Model


- The page owns the game WebSocket lifecycle. The bot must not create or reconnect a second socket.
- Control should use the page/native WebSocket and native page state when available. The bot may send `vel` and `shoot` messages directly on the existing native page WebSocket for lower command-path overhead, but it must not create or reconnect a second socket.
- A current user id plus page/native WebSocket in `CONNECTING` or `OPEN` state counts as an active page game session for login/status purposes, even if `tmpGameSessionToken` is unavailable. The exception is a fresh `graspRatNoSelfSnapshotRecovery` marker written after snapshot-confirmed server-side exit; while that marker matches the current user and self is still missing, stale token/native-session evidence is ignored so automatic login can run.
- Confirmed exits and successful/HTTP 403 leave completions must stop game-operation motion immediately. The stop path clears native movement keys, velocity vectors, `lastVel`, touch movement, and any pending precision pulse timer before the bot continues relogin/hold bookkeeping.
- Tampermonkey and extension bootstraps can pass persisted runtime config to the remote bot, including combat logging enabled/address.
- Bootstrap panel follows the native left-side panel visual language: 336px right rail, 16px radius, translucent dark rail background, native monospace font, status dot, compact dot pause/resume control, and compact metric cards for session uptime/stamina spent/coins/kills.
- Bootstrap panel header uses compact dots: `BOT` dot toggles pause/resume, `WS` dot shows online/connecting/offline state, the remote-log dot toggles combat logging, and a compact dynamic-width network-quality pill follows those controls before the right-side GitHub link. The network pill displays `latency/loss` such as `123ms/0.00%`, using `??ms/??.??%` until samples exist; latency and loss are colored independently and the slash remains white. The clock row only shows current time. The displayed latency is an effective game latency estimate that prefers recent movement action confirmation and falls back to native WebSocket state-frame timing; displayed packet loss is estimated from native WebSocket state-frame long gaps over the rolling runtime window.
- `status().networkQuality` exposes the full rolling estimate: displayed latency/loss, latency/loss source labels, native WebSocket frame interval/jitter/gap counts, current stall state, and movement/attack action feedback counters. The state is in-memory only and is intentionally recomputed after reload or hot update.
- `status().actionSettlementStall` exposes the in-memory detector for the case where the native WebSocket still receives state frames and local movement/shot intent continues, but the game does not settle actions: self position, HP, stamina, coins/Drop, and combat target HP stay unchanged while movement acknowledgements are stale. When `actionSettlementStallOfflineEnabled = true`, a stalled state is handled by the normal offline leave path with the same safe/unsafe wait timing as websocket offline.
- `status().targetSwitchDiagnostics` exposes the in-memory final-action focus history used to diagnose target oscillation. It preserves `lastFocus`, `lastTargetFocus`, `lastSwitch`, and a capped recent `events` list across hot updates; standalone combat-log `target-switch` misc entries are emitted only when combat logging is enabled.
- `status().finalActionArbitration` exposes the final action arbitration state. It preserves `lastAction`, `lastFocus`, `lastSelectedAt`, `lastOverride`, and a capped `history` list across hot updates so short cross-band stick decisions can be inspected after live oscillation samples.
- Remote-log dot is green when logging is enabled, green blinking when entries are pending, yellow when disabled, and red after recent flush failures.
- Metric cards show values only; labels are exposed through `title` and `aria-label`.
- The HP line shows the three stamina windows as native remaining/limit pairs without 5s/1h/1d labels.
- Session stamina spent is derived from observed 1d stamina max/min inside the current login and tracked across UTC+8 daily resets. Runtime today totals and generated daily reports also retain the latest 1d remaining/limit pair and prefer the actual daily delta (`stamina1dLastLimit - stamina1dLastRemaining`) when it is higher than the summed per-login deltas, so mid-day logins do not undercount full-day stamina consumption.
- Important summary logs persist locally under `localStorage.graspRatImportantLogs` with `sessions`, `combats`, and replayable `events`. They record login/exit summaries, stamina/coin/kill totals, per-kill reward details, pure refreshed coin estimates, and combat HP start/end/min/max/deltas/results. Session payloads include `stamina1dObservedMax`, `stamina1dObservedMin`, `stamina1dLastRemaining`, and `stamina1dLastLimit` for report reconciliation. Per-kill summaries include `rewardConfirmed`/`dropMatched` for local picked-reward evidence, `chatConfirmed`/`killConfirmed` for confirmed kills that may not have been picked, and optional non-combat battle-window fields (`battleStartedAt`, `battleEndedAt`, `battleDurationMs`, `battleStaminaSpentMs`) for daily actual battle profit rows. The daily report treats local reward evidence conservatively and can demote over-budget rewards to unpicked Drop when session collected coins cannot cover them. Combat HP start/min/max fields use the first observed valid HP value and must not treat missing `null` as zero. When a combat-log endpoint is configured, these `important-log` events are posted to the same `/combat-log` service as non-critical logs even if normal combat logging is disabled.
- Remote bot post-login zoom state is exposed in `status().postLoginZoom`; after self is missing for at least 1s, the next alive self detection schedules a visible-range fit pass after a 350ms resize-stabilization delay. The fit pass measures the current projection, target blue view-circle radius (`postLoginZoomFitRadiusCm = 50000`), and available `.map-shell` room around self. The target is now close to full visible fit (`postLoginZoomFitTargetRatio = 0.98`, tolerance `0.04`, clamped to `maxRatio = 1.00`): if the circle is clipped (`fitRatio > maxRatio`) it sends a small centered zoom-out wheel step, and if the view was zoomed out too far (`fitRatio < minRatio`) it sends a small zoom-in wheel step. Wheel steps are slower and smaller (`postLoginZoomWheelDeltaY = 35`, `postLoginZoomOutIntervalMs = 220`), and every wheel/button fallback action is followed by a fresh measurement before another zoom action is sent. Once the circle is inside the target band, it finishes with `visible-range-fit`. `postLoginZoomOutClicks = 5` remains only the fixed fallback when measurement is unavailable, and those clicks are now queued one at a time with rechecks when measurement becomes available. The `postLoginZoom` state is preserved across remote bot hot updates, so script replacement while already in-session does not re-trigger zoom.
- When the page is already logged in/reconnecting but self entity is not visible yet, the remote status reports `game-session-connecting` with display reason `已登录，等待游戏连接/自身实体` instead of `login-cooldown`.
- A logged-in/session-present no-self state is unsafe when native WebSocket reconnect churn is detected or the own entity stays missing for `gameSessionNoSelfLeaveMs = 30000`. If a fresh page-native `/snapshot` still contains the current self, the bot treats this as a live session/mismatch problem; if the fresh snapshot is authoritative and self is absent, it confirms the server-side exit, clears stale local/session login keys (`tmpGameSessionToken`/`tmpGameUserId`), writes `localStorage.graspRatNoSelfSnapshotRecovery`, closes the page WebSocket, and refreshes instead of calling `leave()` again. After reload, that marker suppresses repeat leave/session-mismatch handling and the generic reconnecting-session wait, ignores stale generic post-login suppress, and lets gated auto-login proceed even if the page still shows a reconnecting native session. Other no-self timeout/churn cases still use the offline leave path.
- Native WebSocket reconnect churn is tracked from page WebSocket object/state transitions. Three offline-ish reconnect events within 10s count as `control-ws-reconnect-churn`.
- `loginSnapshotGate` is exposed in status/log context and remains the automatic relogin gate wrapper, but standalone `/snapshot` connectivity no longer has an independent 3-sample pass condition. Exit trigger and exit confirmation reset the learned login-point safety evidence; future ordinary unattended relogin is then blocked only until learned login-point safety is satisfied. Explicit manual login from the sidebar/native control is the exception: it records `manualLoginBypass` diagnostics and can bypass snapshot/login-point gates, pause state, suppress, and cooldown. `loginPointSafety` is a durable persisted gate under `localStorage.graspRatLoginPointSafety`: every successful post-login/session-recovery alive-self coordinate refresh updates the persisted login point, and exit/gate resets clear only the safety streak/evidence, never the point. Runtime hot updates preserve `lastLoginAt`, localStorage coordinates are merged back even if in-memory state is empty or stale, newer persisted `lastExitSelfHp` context is merged back after hot updates, and reset `at/reason` plus last-exit HP context is persisted through reloads. When a point is present, future unattended relogins require `loginPointSafetySuccessRequired = 3` consecutive successful page-native `/snapshot` responses with no dangerous player inside the active radius; a `/snapshot` error or unsafe sample resets this streak to `0`. The relogin gate does not actively fetch `/snapshot`; its passive observer avoids wrapping `window.fetch` and `XMLHttpRequest.send`, then reads parsed page fetch responses through `Response.json/text` and page-owned XHR responses through a load listener installed from `open`. Snapshot errors clear stale `lastDanger` so the visible block reason is either the current player danger or the current snapshot error, not both. The radius is `loginPointSafetyHealthyRadius = 17000` only when the last recorded exit HP is at least `loginPointSafetyHealthyHpThreshold = 80`, otherwise it is the conservative `loginPointSafetyRadius = 30000`. Unknown last-exit HP is treated as low HP and uses `30000`. When no point is available, status reports `missingPoint` and the safety gate is not satisfied. Dangerous players are limited to same-day recorded damage actors and `Active` mode players with observed activity evidence; same-day damage actors are persisted only from self-HP-drop evidence that identifies the actor by incoming bullet ownership, firing evidence, or engaged-combat evidence. Pure join-mode `Active` no longer blocks by itself: the Active-mode gate requires firing, movement/speed or observed login-point movement, 5s stamina below the full threshold, or engaged-combat flags. `status().reloginGate` summarizes the visible pre-login gates for panel/log inspection without changing decisions: cooldown/suppress/hold remaining versus total and login-point safety streak out of 3 with missing-point, danger, error, active radius, and last-exit HP details. Once an alive self appears after entry, the login-point gate remains pre-login only; normal movement/combat/exit logic handles post-entry safety.
- `sessionMismatchRecovery` is exposed in status when the page/auth UI and native game session disagree. A low-risk timed-out session mismatch first writes one refresh attempt to `localStorage.graspRatSessionMismatchRecovery`; after a page load whose `performance.timeOrigin` follows that request, the same-user mismatch may proceed to the existing guarded takeover path. The marker expires after `sessionMismatchRecoveryReloadMaxAgeMs` and is cleared once self is restored or the mismatch resolves.
- Stale enemy/offline relogin holds are cleared when the page has recovered to an alive self entity and an online native WebSocket, so the panel no longer shows an old wait reason or keeps the bot stopped after recovery.
- Bootstrap manifest polling defaults to 10s. Tampermonkey request transports and raw/jsDelivr fallback URLs are tried sequentially, so a successful poll should issue only one manifest network request instead of parallel duplicate raw GitHub requests.
- Bootstrap watchdog checks a running bot's version/hash/tick health every second. When a bot is stale but still running with its timer active, the watchdog first probes `bot.step('bootstrap-watchdog-stale-probe')` and rechecks status before reinstalling cached source, so ordinary timer delay does not cause repeated same-version hot replacement.
- Ordinary in-game global refresh no longer actively fetches `/snapshot` or `/minimap`. `globalRefreshMs = 5000` only throttles passive-refresh diagnostics; runtime state is updated from native/realtime page state plus page-native `/snapshot` responses observed without wrapping request send paths.
- The old movement-time server-position forced refresh probe has been removed. Movement no longer triggers extra `/snapshot` or `/minimap` requests.
- Local/native page data is authoritative near the bot. Snapshot data is for outside-local awareness only.
- Combat target, aim, and fire decisions use native/realtime visible entities and bullets only. Realtime visual range is larger than attack range, so combat does not need snapshot data.
- Ordinary profit routing considers native/realtime visible coins and visible AFK targets. It no longer falls back to far snapshot coins or snapshot/minimap Drop targets; if no visible/native coin or acceptable visible target exists, the bot waits for visible coin refresh.
- `opportunityAfkStamina` is an in-memory, hot-update-preserved map keyed by target id. It stores the last observed 5s stamina sample plus a cooldown expiry; observed stamina decreases make only out-of-range AFK opportunity targets ineligible until the 60s cooldown expires.
- For coins specifically: inside the local/view authority radius, do not use `/snapshot` coin drops. Real visible/local coins must come from native page coin state.
- Native coin discovery includes the page render helper `getRenderCoinDrops()` plus native state coin/list fields; it accepts arrays, Map/Set values, object maps, single coin objects, and render/state getter functions. This is the authoritative source for visible viewport coins.
- Snapshot coins may still be classified for diagnostics/outside awareness only. Ordinary coin pickup does not navigate to snapshot-only coins, even outside `nativeCoinAuthoritativeRadius = 50000cm`.
- Native/visible coins must not receive `snapshot-coin-*` reasons even if merged metadata carries snapshot fields.
- Removed local snapshot fallback: no `snapshotCoinLocalFallbackMaxDistance`, no local snapshot/native matching fallback.
