# Combat Logging Notes


- Local collector lives in `combat-log-service/` and uses Node built-in modules only.
- Start collector with `cd combat-log-service && npm start`.
- Enable in game console:

```js
window.__graspRatBotBootstrap.configureCombatLogging({
  enabled: true,
  endpoint: 'http://127.0.0.1:18765/combat-log'
})
```

- Disable with:

```js
window.__graspRatBotBootstrap.configureCombatLogging({ enabled: false })
```

- Tampermonkey persists `combatLoggingEnabled` and `combatLogEndpoint` via `GM_setValue`; the extension persists the same config in extension storage.
- Logs are written to split JSONL paths under `combat-log-service/logs/YYYY-MM-DD/<kind>/<combatId>.jsonl`, where `<kind>` is usually `combat`, `important`, `audit`, or `misc`; this directory is ignored. Start the collector with `node server.js --flat-files` only if the legacy `logs/YYYY-MM-DD/<combatId>.jsonl` layout is needed.
- Detailed log retention is automatic: the collector runs cleanup at startup and then daily at local `03:30`, keeping only the latest 3 local date directories of detailed `combat`/`misc` JSONL and legacy flat combat JSONL. `important`, `audit`, and `daily-*.md` are retained for daily reports and exit audits. Manual maintenance uses `cd combat-log-service && npm run cleanup`, with `-- --dry-run` for preview.
- Analyze collected logs with `cd combat-log-service && npm run analyze`; use `-- --latest 10` for recent exits and `-- --fail-on-issue` for a non-zero exit when missing top-level `exit` or unsafe-delay issues are found.
- The analyzer now streams JSONL in chunks instead of reading each file into one giant string, so very large historical log directories can still be audited without hitting Node's single-string size limit.
- Continuously monitor collected logs with `cd combat-log-service && npm run monitor`; use `-- --watch-count 1` for a finite smoke check and `-- --watch-interval-ms 5000 --latest 5` to tune polling/noise.
- Current manifest-version commands: `cd combat-log-service && npm run analyze:current`, `npm run validate:current`, `npm run validate:objective`, `npm run monitor:current`, `npm run monitor:current:strict`, `npm run monitor:objective`, `npm run monitor:objective:fresh`, and `npm run monitor:objective:observe`; use `npm run monitor:objective:fresh` to ignore old logs, require fresh current-version exit/combat evidence, and monitor only future current-version entries.
- `npm run validate:current` and one-scan `npm run monitor:current:strict -- --watch-count 1` require at least one current manifest-version log entry and exit non-zero with `no-matching-entries` when current-version logs have not arrived yet; this distinguishes "no issues found" from "no validation evidence".
- `npm run validate:objective` and one-scan `npm run monitor:objective -- --watch-count 1` also require at least one current manifest-version exit event, one Active-in-range combat-response event, and one HP-disadvantage combat exit event. They exit non-zero with `no-matching-exit-events`, `no-active-in-range-combat-events`, or `no-hp-disadvantage-exit-events` when current logs exist but those samples are missing.
- Active-in-range behavior audits distinguish actionable realtime evidence from snapshot-only context. `coin-action-with-active-player-in-range` is emitted only when the in-range Active player is backed by `native`, `render`, `realtime`, or current strict target evidence; snapshot-only Active players may still appear in nearby context but do not count as a combat/coin regression because combat target, aim, and fire decisions cannot use snapshot authority.
- `npm run monitor:objective:observe -- --watch-count 1 --watch-interval-ms 250` currently exits zero with only missing-evidence status when no fresh `.109` logs exist. Use it for long-running observation after release; use `monitor:objective:fresh` / `validate:objective` when missing evidence should fail the run.
- `node scripts/objective-status.js --fail-on-incomplete` is the current completion gate. It currently reports static build `ok`, but overall `not complete` because live evidence has `entries=0/18851`, `exits=0`, `unsafeOrRequiredDelayExits=0` in human output (`unsafeOrRequiredDelayExitEvents=0` in JSON), `activeCombat=0`, and `hpDisadvantageExits=0` for `bootstrap-0.4.109`. Requirement output is now granular: exit/relogin evidence and Active/HP combat evidence are reported independently.
- Manifest-based analysis now also checks matching log `sourceHash` values against manifest SHA-256 and reports `manifest-source-hash-missing` / `manifest-source-hash-mismatch` evidence issues.
- Combat decision logs expose live/native/render aim evidence under `decision.aimTarget`, including strategy, strategy reason, live distance, source divergence, server-stall, `liveInterceptAim`, radial precision, real-bullet precision, and fallback precision fields. `strategyReason=real-bullet-pressure-intercept` and `strategyReason=server-stall-live-intercept` mark the new lateral live-intercept branch. Current combat decisions do not expose snapshot aim authority because combat no longer consults snapshot data for target, aim, or fire decisions.
- `npm run replay` reports actual-shot aim scenarios plus `finish-pressure hypothetical dynamic vs live target` for old low-HP retreating-edge windows. Use that line to validate whether a proposed finish-pressure change adds plausible hits where the old log had no shots or only retreating-edge suppression.
- `nearbyEntities` summaries preserve realtime/native/render coordinates when a later snapshot record has the same player id. Snapshot records may still mark `snapshot:true` and fill missing HP/drop fields, but they must not overwrite the realtime coordinates used by combat target, aim, fire, and replay review.
- Important daily combat summaries record HP start/end/min/max/deltas for self and target. Starting HP is filled from the first valid observed HP sample, including later samples if the combat opened before HP was available; missing `null` is not a numeric zero.
- Important kill summaries now carry optional battle-window fields for non-combat Drop kills: `battleStartedAt`, `battleEndedAt`, `battleDurationMs`, `battleStaminaSpentStartMs`, `battleStaminaSpentEndMs`, and `battleStaminaSpentMs`. These are derived from recent attack history so the daily report can show actual fight time/stamina for future AFK/ordinary Drop kills. Older logs without these fields still support kill/profit attribution, but standalone non-combat kill rows may show unknown stamina.
- Daily active-combat result text should use mutually exclusive top-level outcomes: `胜利`, `失败`, `我方主动退出`, `敌方逃离`, and `目标切换`. Text after the colon is evidence within that outcome, not another competing result. Post-combat recovery waits and `post-combat-timeout` target loss are folded into `敌方逃离`, including targets that leave, teleport, disappear, or move out of range. Safety movement that avoids invulnerable targets is not combat and is filtered out of the active-combat table, including legacy `recovery-avoid-humans` closures.
- Daily summaries merge `session-end` and `exit-audit` evidence before rendering exit reasons. Specific combat, injury, stamina, offline, and pursuit reasons take priority over later `no-self` or `login-before-session-end` closeout records, and `enemy-leave-wait` combat rows should include the concrete exit evidence plus HP changes instead of only saying that the bot waited for safe relogin.
- Daily summaries treat explicit `pickedCoins=0` as authoritative and fall back to `coinsGained` only when pickup totals are missing. They recompute refresh-coin totals from normalized collected coins minus attributed kill rewards, so placeholder short sessions with zero pickup evidence no longer render as fake `1000币` refresh/total收益 rows.
- Daily summaries include a third `实际战斗收益统计` section in addition to login and active-combat tables. It now renders as a Markdown table, lists only confirmed kills and battle failures/HP-disadvantage exits, excludes enemy-flee/target-switch/safety-avoidance rows, and reports actual picked reward separately from unpicked confirmed Drop or failed unearned Drop.
- Reason-specific delay auditing currently treats `stamina-budget-coin-leave` as requiring 30 minutes by default; use `--stamina-budget-delay-ms <ms>` if that config changes.
- For current-version validation, filter historical noise with `npm run monitor -- --min-version bootstrap-0.4.104 --latest 10` or start clean from invocation time with `npm run monitor -- --since now --min-version bootstrap-0.4.104 --latest 10`.
- Current local old logs (`bootstrap-0.4.71` through `bootstrap-0.4.96`) show 50 exit events, all missing top-level `exit`, and 39 unsafe exits below the 60s delay evidence; this is expected historical evidence and not validation of latest `bootstrap-0.4.109`.
- `bootstrap-0.4.93` historical safety counts show `unsafe=23`, `unsafeDelayOk=0`, `unsafeDelayBelowMin=23`, and `unsafeDelayMissing=23`; reason counts show exits dominated by `injury hp drop=14`, then `cooldown=6`, then `login-suppressed=3`; behavior reason counts show `wait-for-clear-opportunity=6` events covering 902 frames and `best-opportunity-coin=2` events covering 30 frames; Active-in-range combat evidence shows 24 events; HP-disadvantage exit evidence shows 0. This validates the analyzer and old-root-cause explanation, not the current bot.
- If the collector is unavailable, the bot keeps the bounded pending queue, records failure status in the panel/status, and does not affect combat decisions.
